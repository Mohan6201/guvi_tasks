This document records the deployment of the Trend App (a React e-commerce demo, "Trendify") to Amazon EKS through Terraform-provisioned infrastructure and a Jenkins-driven CI/CD pipeline. Terraform provisions the VPC, IAM roles, the EKS cluster/node group, and the Jenkins EC2 instance from a single .env file. Jenkins then builds the Docker image, pushes it to DockerHub, and deploys it to EKS via kubectl, triggered automatically on every GitHub push through a webhook. The report follows the actual order of execution — the commands run, the real configuration files used, the console/CLI output captured at each step, the two failed pipeline builds and the issues that caused them, and the monitoring stack built on Prometheus/Grafana once the app was live. All AWS infrastructure was destroyed after verification to avoid ongoing charges (Section 18).

1. Objective

Deploy the Trend App (a pre-built React/Vite e-commerce frontend) to a production Kubernetes environment on AWS, with infrastructure defined as code and a Git-triggered CI/CD pipeline: a commit to GitHub should build a Docker image, push it to DockerHub, and roll it out to an EKS cluster automatically via Jenkins, exposing the app through a public load balancer. The task requirements are: a Dockerfile and local image verification, Terraform-provisioned VPC/IAM/EC2-with-Jenkins infrastructure, a DockerHub repository, an EKS cluster with deployment/service manifests, Jenkins installed with the Docker/Git/Kubernetes/Pipeline plugins, a GitHub webhook triggering builds on every commit, a declarative pipeline building, pushing and deploying via kubectl, version control on GitHub, and open-source monitoring of the cluster/application.

4. Terraform — VPC, IAM, EKS Cluster & Jenkins EC2

A single main.tf provisions the entire base infrastructure: a VPC with 2 public + 2 private subnets across two Availability Zones, four IAM roles (EKS cluster role, EKS node role, and a dedicated Jenkins EC2 role with an EKS access entry so Jenkins can call kubectl without any static AWS keys), the EKS cluster and managed node group, and the Jenkins EC2 instance itself (bootstrapped via a templated user-data script). EKS access uses API_AND_CONFIG_MAP authentication with bootstrap_cluster_creator_admin_permissions = true, and the Jenkins role is granted AmazonEKSEditPolicy cluster access — enough for namespaced kubectl apply/set image operations without full cluster-admin.

terraform/main.tf (Core Resources, As Committed To The Repository)

5. Application Source, Docker Image & Local Verification

The upstream Trend repository intentionally ships only a pre-built dist/ — its own README explains there is no source/package.json, by design, so learners focus on deployment rather than app development. That means dist/ is the source as far as this deployment is concerned, and it had to be committed to git (Section 13.2) — a normal .gitignore would exclude it as a build artifact.

The shipped bundle also has one real bug baked into its minified JavaScript: product thumbnails are requested from a broken relative path undefined/images/<name>.png — an unset base-URL environment variable that got stringified literally as "undefined" at build time, upstream, before this project ever touched it. Since there is no source to rebuild from, the fix is applied at container build time in the Dockerfile: every product image is duplicated under the exact broken path the bundle requests, using Vite's fixed-length asset hash to recover the original filename.

Dockerfile (Full File, As Committed To The Repository)
# Use nginx as a lightweight web server
FROM nginx:alpine

# Copy the built React app from dist folder to nginx's html folder
COPY dist/ /usr/share/nginx/html/

# The vendor-shipped production build (no source available to rebuild)
# has a baked-in bug: product thumbnails are requested from a broken
# relative path `undefined/images/<name>.png` - an unset base-URL env
# var that got stringified as "undefined" at build time. Recreate that
# exact path here (not in the gitignored dist/ folder) so the fix is
# git-tracked and survives fresh clones / Jenkins builds, not just this
# machine. Vite doesn't alter image bytes when hashing, only renames -
# it always appends a FIXED 8-character hash (from a base64url-like
# alphabet that itself can contain "-", e.g. "p_img47-C0-ZYjIt.png" is
# "p_img47" + hash "C0-ZYjIt") - so stripping exactly the last 9
# characters ("-" + 8-char hash) before the extension recovers the
# plain name, unlike a naive "strip after the last hyphen" approach
# which breaks whenever the hash itself contains a hyphen.
RUN mkdir -p /usr/share/nginx/html/undefined/images && \
    for f in /usr/share/nginx/html/assets/*.png; do \
      plain=$(basename "$f" | sed -E 's/.{9}\.png$/.png/'); \
      cp "$f" "/usr/share/nginx/html/undefined/images/$plain"; \
    done

# Copy custom nginx configuration
COPY nginx.conf /etc/nginx/nginx.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
nginx.conf (Full File, As Committed To The Repository)
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    # Cache-Control: no-cache on everything non-hashed, so a browser
    # that loaded a broken response once (before a fix was deployed)
    # doesn't keep serving it from disk cache indefinitely.
    location / {
        add_header Cache-Control "no-cache";
        try_files $uri $uri/ /index.html;
    }
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # The bundle's broken image src is a RELATIVE path, so the browser
    # resolves it against whatever route is open - "/" and "/collection"
    # resolve fine, but "/product/<id>" resolves one level deeper to
    # "/product/undefined/images/x.png" instead. This regex location
    # matches ".../undefined/images/<file>" at ANY route depth.
    location ~ ^.*/undefined/images/(.+)$ {
        add_header Cache-Control "no-cache";
        alias /usr/share/nginx/html/undefined/images/$1;
    }
}

12. Declarative Pipeline — Jenkinsfile

Five stages: Checkout, Build Docker Image, Test Docker Image, Push to DockerHub, Deploy to EKS. checkout scm pulls the entire monorepo, but the Dockerfile and k8s/ manifests only exist under Project-2/Trend — so the Build and Deploy stages scope into that subfolder via a Groovy dir() block driven by the SOURCE_DIR global environment variable, exactly mirroring how Terraform and the app itself are already .env-driven.

jenkins/Jenkinsfile (Full File, As Committed To The Repository)
pipeline {
    agent any
    environment {
        DOCKERHUB_CREDENTIALS = credentials('dockerhub-creds')
        IMAGE_NAME  = "${DOCKERHUB_CREDENTIALS_USR}/trend-app"
        IMAGE_TAG   = "${env.BUILD_NUMBER}"
        EKS_CLUSTER = "${env.EKS_CLUSTER_NAME}"
        AWS_REGION  = "${env.AWS_DEFAULT_REGION}"
    }
    stages {
        stage('Checkout') { steps { checkout scm } }

        stage('Build Docker Image') {
            steps {
                script {
                    // checkout scm pulls the whole monorepo, but Dockerfile
                    // only exists under this subfolder - SOURCE_DIR is a
                    // Jenkins global env var (Manage Jenkins > System).
                    def srcDir = env.SOURCE_DIR ?: '.'
                    dir(srcDir) {
                        sh '''
                            docker build -t ${IMAGE_NAME}:${IMAGE_TAG} .
                            docker tag ${IMAGE_NAME}:${IMAGE_TAG} ${IMAGE_NAME}:latest
                        '''
                    }
                }
            }
        }

        stage('Test Docker Image') {
            steps {
                sh '''
                    docker run -d --name trend-test -p 8081:80 ${IMAGE_NAME}:${IMAGE_TAG}
                    sleep 10
                    curl -f http://localhost:8081 || (docker logs trend-test && exit 1)
                    docker stop trend-test && docker rm trend-test
                '''
            }
        }

        stage('Push to DockerHub') {
            steps {
                sh '''
                    echo "$DOCKERHUB_CREDENTIALS_PSW" | docker login -u "$DOCKERHUB_CREDENTIALS_USR" --password-stdin
                    docker push ${IMAGE_NAME}:${IMAGE_TAG}
                    docker push ${IMAGE_NAME}:latest
                '''
            }
        }

        stage('Deploy to EKS') {
            steps {
                script {
                    def srcDir = env.SOURCE_DIR ?: '.'
                    dir(srcDir) {
                        sh '''
                            aws eks update-kubeconfig --region ${AWS_REGION} --name ${EKS_CLUSTER}
                            kubectl apply -f k8s/
                            kubectl set image deployment/trend-app trend-app=${IMAGE_NAME}:${IMAGE_TAG}
                            kubectl rollout status deployment/trend-app --timeout=120s
                        '''
                    }

16. Monitoring — Prometheus & Grafana

Both deployed to a dedicated monitoring namespace via monitoring/setup.sh: Prometheus scrapes kube-state-metrics (cluster object state) and the kubelet's cAdvisor endpoint (per-pod/per-node resource usage) via its own ClusterRole; Grafana visualizes it. Three real issues surfaced while getting this working, in order.

⚠ Issue 1 — Prometheus RBAC missing entirely
level=ERROR msg="Failed to watch" err="failed to list *v1.Pod: pods is forbidden:
User \"system:serviceaccount:monitoring:default\" cannot list resource \"pods\"
in API group \"\" at the cluster scope"
The original manifest ran Prometheus as the namespace's default ServiceAccount, which has zero Kubernetes API permissions — so kubernetes_sd_configs-based service discovery (for pods and nodes) found zero targets.
✓ Fixed
Added a dedicated ServiceAccount + ClusterRole (get/list/watch on nodes, nodes/proxy, services, endpoints, pods) + ClusterRoleBinding, and set serviceAccountName: prometheus on the Deployment.
⚠ Issue 2 — Grafana losing all dashboards on every restart
Grafana was being OOMKilled (exit code 137) — it needs ~350-450 MB, the manifest only allowed 256Mi — and had no persistent volume, so its SQLite database (all dashboards/datasources) lived only in the container's writable layer and was wiped on every crash. Fixing the PVC then surfaced two further layers: the EBS CSI driver was not installed on this cluster at all (aws eks list-addons returned empty — mandatory since Kubernetes 1.23 removed the in-tree provisioner), and once installed, its controller pods crash-looped with no EC2 IMDS role found — the classic EKS gotcha where the instance-metadata hop limit defaults to 1, blocking pods (not just the host) from reaching IMDS.
✓ Fixed
$ aws iam attach-role-policy --role-name trend-eks-node-role \
    --policy-arn arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy
$ aws eks create-addon --cluster-name trend-eks-cluster --addon-name aws-ebs-csi-driver
$ aws ec2 modify-instance-metadata-options --instance-id <node> \
    --http-put-response-hop-limit 2 --http-tokens required
$ kubectl delete pods -n kube-system -l app=ebs-csi-controller   # picks up new setting
ebs-csi-controller-...   6/6   Running   0
Plus a PersistentVolumeClaim for /var/lib/grafana, memory limit raised to 768Mi, and securityContext.fsGroup: 472 (the official Grafana image's non-root uid) so the freshly-provisioned, root-owned EBS volume is actually writable. Verified by deleting the Grafana pod outright and confirming both dashboards survived the restart.
⚠ Issue 3 — Imported community dashboard mostly showed N/A
Dashboard ID 3119 ("Kubernetes cluster monitoring via Prometheus", published 2017) hardcodes Docker-era labels (name=~"^k8s_.*", grouped by io_kubernetes_pod_name) that containerd — the runtime on modern EKS nodes — never sets, plus a hardcoded filesystem device /dev/vda9 that doesn't match this account's Nitro-based /dev/nvme0n1p1. 9 of its 13 panel rows were permanently incompatible.
✓ Fixed
Built a single consolidated dashboard, "Trend Cluster Health", with every panel query hand-verified against the Prometheus API before saving: cluster CPU/memory/filesystem %, node count, per-pod CPU/memory (using the correct modern pod/ namespace/container labels), and running pods per namespace.
